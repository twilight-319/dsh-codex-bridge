# 减少协调开销

RC.6 / Codex 0.9.0 默认返回后台交办回执。用户要求在对话内接结果时，使用程序续等的 `dsh_task_observe` 并设置外层执行器预算。以下保留各项基础能力与用量口径。[双向协作产品规划](PRODUCT_PLAN.md)

本次改造针对简单任务委派后 Codex 仍持续处理等待、两端重复工作、用量不透明的问题。该轮改造尚未安装到运行中的 DSH 或 Codex 缓存，也未作为稳定版发布。真实长调用、模型用量和产物质量对照仍待验收，发布状态保持 NO-GO。

## 执行模式

- `direct`：默认直接交给 DSH。保留用户目标和限制，执行后不自动调用 Codex 审查。
- `planned`：调用方已经完成必要规划，把非空计划放进 `plan`。服务端将目标、计划、验收要求一并交给 DSH，不另行调用模型生成计划。
- `reviewed`：DSH 完成后调用已有 Codex 审查器，增加模型参与。允许附计划，不能与 `review:false` 冲突。

省略模式时兼容原参数：`review:true` 对应 reviewed，否则非空 plan 对应 planned，其余 direct。旧幂等凭据仍先匹配原记录，不因新组合长度限制阻止查询旧提交。新提交的目标、计划和验收条件合计最多20000字符。不会自动改变模型、思考档位、权限或验证配置。

工作台新增模式选择与开销说明。直接执行表单不提交隐藏计划；审查模式才启用额外 Codex 调用。执行完成与验收通过继续分开记录，未配置验证仍可为 REVIEW_REQUIRED，不能冒充 SUCCEEDED。

## 长等待与兼容

新增 `dsh_task_await`，只在以下情况返回：终结、当前问题、原生审批、需要对账、绑定 Run 改变、宿主关闭或等待到期。运行进度、模型选择证据、用量更新不会提前结束长等待。

```json
{"taskId":"task-...","runId":"run-...","waitMs":600000}
```

等待范围0～600000毫秒，默认600000。它与任务执行 deadline 分开：等待过期、取消 MCP 等待或连接中断不请求停止后台任务，也不重新派发。显式取消任务继续使用 dsh_task_cancel。原 dsh_task_wait 保留0～25000毫秒、默认按 revision 返回的旧行为，也可传 until=actionable。

仓库 .mcp.json 已有 tool_timeout_sec=620，足以覆盖600秒等待及10秒传输余量；实际客户端能否完整保持该调用仍需真机确认。仅已确认不支持长调用的客户端应显式使用 waitMs=55000；不要仅因未知就默认回到模型短轮询。不要假称 MCP 通知能自动唤醒结束的模型回合。客户端提供 progressToken 时仅发送协议进度心跳，不结束工具调用。

两端须一起更新；旧 DSH 没有 await 路由时会明确失败，不回退旧同步执行工具。旧 dsh_execute 的600秒到期取消语义保持不变。

## 精简结果

MCP 任务工具默认 detail=summary，返回凭据、状态、执行完成事实、验证/审查状态、最多4000字符结果、已验证产物位置、用量与耗时，以及需要处理的问题/错误。结果截断会标记 textTruncated，产物列表最多50条并标记是否截断。

需要完整记录时：

```json
{"taskId":"task-...","detail":"full"}
```

默认结果形状与旧版完整 Task 不同，依赖 run/tuning/history 的 MCP 调用方应显式传 full。HTTP任务核心和浏览器工作台仍取得完整记录。detail 在 MCP 层移除，不进入提交幂等哈希。只读工具提供 readOnlyHint；这是能力提示，不替代客户端审批策略。

## 用量与时间的口径

DSH 用量来自当前 Run baseline 之后的 durable assistant/message.data.usage，以事件 seq 去重；回答问题后的执行只统计新增事件，然后累积到同一 Run。没有 usage 的 assistant/attempt 或消息会使覆盖状态为 partial/unknown。历史分页可能限制可观察范围，因此 coverage 明确为 observed-assistant-records-only，不能把已观察的计数冒充服务商全账单。

当前 DSH TokenUsage 的 inputTokens **只含未缓存输入**，cacheReadTokens/cacheWriteTokens 分开。各字段只在证据存在时累加；缺失值保留 null，totalTokens 不按猜测补齐，cost 固定未知。与 Codex 输入含缓存的计数口径不同，不能直接相加当作费用。

桥内 Codex 审查记录现有 runner 返回的用量和缓存字段。外部 Codex 规划、协调及订阅额度未接入，明确显示未知；等待调用次数也不等于 GPT 模型调用次数。

记录 queueMs/executionMs/humanWaitingMs/verificationMs/reviewMs/totalMs，缺失阶段不伪造。排队时间包括首次准备前等待，executionMs 是宿主执行调用耗时，包含工具和模型活动；并非纯模型推理时间。普通进度仍在工作台每5秒刷新，由程序读取，不需要模型参与。

等待调用计数保存在当前宿主内存，随下一次任务事件写入检查点，避免每次只读等待都改 revision 并制造新轮询。宿主中断可能丢失尚未保存的计数；不宣称精确持久化账单。observerMs 是各等待请求耗时之和，可与执行时间重叠，不加进总任务耗时。

## 验证与后续实测

离线测试覆盖进度不打断长等待、等待到期/取消不停止任务、不重复派发、三种模式的实际审查调用、计划和验收传递、摘要/full、幂等回放、缓存口径、持续问答去重，以及真实 MCP stdio 到模拟 HTTP 的取消链路。工作台采用 React 行为契约验证，不作为视觉验收。

真实对照固定模型、档位和任务范围，分别运行：DSH原始需求、DSH使用一次Codex制作说明、插件使用同一制作说明、Codex单独执行。记录产物质量、两端可取得用量、缓存、费用与阶段耗时；多次运行后再评估收益。本地改造不自动启动付费模型对照，不承诺固定节省比例。

正式启用前按现有维护排空流程处理 DSH 在途任务，再更新双端、重启/重连 MCP。保留原生问题、审批、对账和恢复边界，不为升级取消正在运行的任务。
