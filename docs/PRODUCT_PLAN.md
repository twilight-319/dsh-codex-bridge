# Codex × DSH 双向协作产品规划

2026-11-18 · 双向协作候选为 DSH 桥 2.0.0-rc.6 和 Codex 插件 0.9.0 · 真实账户配对验收待完成

**用户承诺。** 在 Codex 里，把实现交给价格更低的 DSH。在 DSH 里，把值得花 GPT 额度的难题交给 Codex。用户从惯用的入口提出需求，拿到能用的结果，并能看清 Codex 在哪里参与、解决了什么问题。

优化顺序是先守住用户的验收要求，再减少每个合格交付消耗的 Codex 额度，同时控制从提出需求到拿到可用结果的总时间。DSH 可以多读文件、多做验证。如果它反复试错，或者用户为了省额度反而要花更多时间盯进度，这条路径就需要调整。

**为什么优先改交办。** 11 月 17 日的一次单文件动画任务中，桥接从接单到交付用了 428 秒，其中 DSH 执行占 362 秒。同需求由 Codex 独立制作用了 249 秒。桥接当时已关闭额外审查。长等待可以减少协调往返，速度还取决于交办说明能否让 DSH 更快做好成品。这个样本没有提供 DSH 独立执行的配对时间。[现场记录](OBSERVATION_QUALITY.md)

## 一、从 Codex 交办给 DSH

用户说“交给 DSH，把订单导出支持按部门筛选”。Codex 确认交付范围，必要时补上影响结果的判断，例如“沿用列表已有的部门权限，不选部门时保持原导出行为”。DSH 自己定位导出入口、查询条件和测试。用户已经给过明确方案时直接沿用。

1. **决定要不要写方案。** 明确的小改动走已有的 `direct`。涉及取舍、多个约束或视觉表现时走 `planned`，用当前 Codex 对话写一次简短交办说明。把目标、关键决定、可观察的验收点和已知相关位置交给 DSH。只有影响决策的未知事实值得 Codex 在交办前查证。
2. **默认后台交办。** 持久化提交成功就给用户任务编号、接手方以及查看位置。首版可用“DSH → Codex → 任务”配合可复制编号。一键定位需要先验证宿主支持。回执写清“已受理”，成品和验证结果随后出现在任务详情。后台交办模式以这张回执结束当前 Codex 回合。
3. **用户决定在哪里接结果。** 需要在当前对话看成品，或明确说“等它完成”的用户，走已有的持续观察工具。常规进度由程序处理。后台任务遇到用户选择或权限审批时，在任务详情标出待办并引导到对应入口。返回原 Codex 对话时也可凭编号按需查询。首版不依赖宿主主动唤醒已结束的 Codex 对话。
4. **沿用同一任务继续。** DSH 自主完成实现和已授权验证，交付改动、产物位置与验证结果。提交回执丢失时用原幂等键取回任务。待答、待审批、执行失败、已完成但未验证分别显示对应动作。额外 Codex 审查由显式请求开启。

用户收到的回执可以写成“DSH 已接手订单导出。任务编号〈编号〉。进度、待答问题和最终文件可在 DSH → Codex → 任务中查看。”如果用户选择在当前对话收结果，回执应说明会继续等待。

## 二、从 DSH 咨询 Codex

用户继续在 DSH 里工作。简单任务由 DSH 独立做完。复杂任务可以在动手前就咨询，例如“给已有审批流程增加多人负责人，历史记录和在途审批都要能继续使用”。DSH 先找出处于变化边界的记录和调用点，然后带着一个会影响实现的决定去问 Codex。

- **理解与拆解。** 目标清楚、实现顺序有依赖时，一次 `codex_plan` 给出建议顺序、最关键的边界和验收点。目标本身取决于用户业务偏好时，直接问用户。
- **方案取舍与解困。** 两个实现会产生不同后果、已有证据互相矛盾，或同一路径重复失败时，使用 `codex_decide` 或 `codex_ask`。DSH 带上现场事实，专家给出一个决定、理由和下一步能验证该决定的动作。
- **定点审查。** 用户要求把关时，使用 `codex_review` 检查指定 diff 和关心的问题。DSH 负责修正并验证。普通成功路径默认结束于 DSH 交付。

**一次好咨询长什么样。** DSH 问“旧审批单保存了负责人快照，新单要支持多人。改实时查部门，还是扩展新单快照？我核对了创建和审批两个入口。”专家可以回答“保留旧单解析，新单创建时冻结多人快照。先用一张在途旧单验证审批人保持原值，再测新单。”DSH 由此可以动手，用户也能理解这次额度换来了什么。

**建议的首版默认值。** DSH 原生入口允许每项任务自动咨询一次，常规任务可以用零次。用户可以关闭自动咨询、主动点名专家，或在出现新证据后追加一次。每次发送前只带任务目标、待决问题、已知事实及必要的文件片段或报错。咨询超时、额度不足或回执未知时，展示已有证据和可继续的动作，避免自动重发。执行权和权限审批留在 DSH。

**方向边界。** Codex 发起的 DSH 执行会话已有防递归保护。它遇到阻塞时，在原任务中记录问题，由用户或原发起方继续处理。DSH 原生入口则可直接咨询。两个方向共用交付标准，避免一次委派在两个模型间反复转手。

## 三、下一版按什么顺序做

### 第一批 · 让用户能放心交出去

复用持久化提交、任务工作台和已有的 `direct / planned / reviewed`。把“谁制定方案”和“在哪里接结果”做成两个独立选择。后台交办与当前对话等待都使用同一个任务。统一插件默认提示、执行技能、MCP 工具说明和工作台文案，消除用户选择交办后仍被指引观察的冲突。首先补齐按编号定位、待处理问题提示和结果入口，再切换默认交互。

验收用一个普通修改和一个需要用户回答的任务。交办返回后关闭原对话，仍能定位任务、处理问题并取回同一份结果。正常后台任务不再由插件要求 Codex 轮询或终审。显式要求等待时仍在原对话交付。旧客户端、已提交任务和现有同步调用继续按其原有契约运行。

相关实现见[默认提示](../.codex-plugin/plugin.json)、[执行技能](../skills/dsh-execute/SKILL.md)、[MCP 工具](../bin/mcp-server.mjs)、[任务摘要](../lib/task-delivery.js)、[工作台](../client.js)。

### 第二批 · 让一次专家意见足以开工

复用现有四个参谋工具，在 DSH 原生咨询入口落实触发条件、材料范围和任务级预算。先确认宿主能稳定标识一次用户任务。会话可以承载多项任务，单用会话 ID 会误伤下一项。无法识别任务边界的宿主先提供手动咨询。预算由程序在派发前记账，重复事件和并发调用共用同一份记录。一次咨询的回执保留问题、决定、用量证据和 DSH 的后续结果。

验收时，普通修改应自主完成。复杂需求在开工前问一次后独立完成。两次相同失败只产生一个咨询请求。专家不可用时 DSH 继续有把握的部分，缺少必要决策时明确停点。额外的用户主动咨询单独记录。

相关实现见[工具注册与防递归](../index.js)、[专家答复格式](../lib/prompts.js)、[上下文采集](../lib/context.js)、[咨询用量](../lib/appserver.js)。

### 第三批 · 用真实交付决定哪些默认值得保留

第一批就开始记录交办时间和后台结束时间，第二批补咨询原因及结果，第三批用这些证据选默认策略。用户在工作台可以逐项核对 Codex 初始交办、桥内专家咨询或审查、DSH 执行、人工等待，以及最终验收情况。旧记录缺字段时显示“未知”。已有多执行者调度继续供能独立拆分的工作使用，首轮验证集中在单任务的两条主路径。

相关实现见[任务计量](../lib/task-usage.js)、[任务状态与耗时](../lib/task-manager.js)、[协调开销口径](EFFICIENT_EXECUTION.md)、[既有等待对照](OBSERVATION_QUALITY.md)。

## 四、怎样证明有价值

小规模配对试验覆盖有客观结果的单点修改、一次设计选择会影响多个入口的功能、过去需要返工的视觉或排错任务。在相同代码快照上使用相同原始需求、执行模型、思考档位、权限和验收标准。先各试一轮发现流程问题，再对有希望的任务类型重复比较。各组从干净状态独立开始。视觉结果隐去生成方式再评价。

1. **测交办。** 比较 Codex 独立完成、Codex 一次说明后桥接 DSH、把完全相同的说明手动给 DSH。后两组都计入生成说明的 Codex 开销，以区分专家指导收益和桥接自身的耗时。
2. **测咨询。** 比较原始需求直接给 DSH、同一需求给允许一次专家咨询的 DSH。记录咨询发生在什么决策点、DSH 采纳了什么、是否少了一轮返工。将原始需求直接给 DSH 的结果也用作前一组试验的质量基线。
3. **按合格交付计账。** 先公布一次通过数、最终通过数、失败数和修复轮数。Codex 和 DSH 分别记录可观察的输入、缓存、输出、调用与相应人工等待。总开销包含失败和返工。耗时从用户提出需求算到首个可验收成品，另记最终通过时间。提交回执延迟单列，观察耗时与执行重叠的部分只算一次。
4. **明确可以得出的结论。** 对能隔离任务且有可靠读数的账户，记录订阅额度前后变化。缺少读数时报告有来源的用量和覆盖范围。HTTP 等待次数、用量事件条数、缓存输入都各用其原意。两端 token 分开呈现，费用以可核实的账单为准。

**采用默认值的判据。** Codex 入口要在同样通过验收的任务上持续减少可观察的 GPT 用量，并且相对“同一说明手动给 DSH”只有用户能接受的额外耗时。DSH 入口要让简单任务保持零咨询，在复杂任务上提高一次通过率或缩短到合格交付的时间。质量、速度和用量分开公布。只有某类任务得到收益，就只在那类任务上推荐。等拿到真实样本再写节省比例和适用范围。

**首轮评审建议。** 每类先做一组配对筛查，值得保留的路径再累计至少三组配对，保留每次结果和中位数。工程上可直接验收两个零值，即后台成功交办后，原 Codex 对话为获取常规进度而再次调用工具的次数为零、DSH 原生简单任务自动咨询为零。对后台交办，建议先用“相对同说明手动执行，额外总耗时不超过 30 秒或对照耗时的 15%，取较大者”作为排查阈值。超过就定位开销发生在哪一段。这是首轮试验的建议值，真实额度与速度优势要由后续结果决定。
